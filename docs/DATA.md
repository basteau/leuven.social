# City data

The map loads a single file, `public/data/city.bin`, which is about 770 KB gzipped for the whole R23 ring plus Heverlee. It is committed, so a fresh clone runs without the raw data. A second file, `public/data/rooms.json`, holds the insides of a few landmarks; it is written by hand rather than built (see [Rooms](#rooms)).

Everything in it can be rebuilt from free, open data with one command: data + code = map. The few things that are not data are listed under [Exceptions](#exceptions).

## Rebuild it

You need [Bun](https://bun.sh) and [uv](https://docs.astral.sh/uv/). uv fetches Python and the pinned packages itself.

| Command              | What it does                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `bun run data`       | All three steps below: fetch, build, bake. About 230 MB of downloads the first time, then seconds.             |
| `bun run data:fetch` | Downloads every source into `data/` and checks it against `data/sources.lock.json`. Skips what it already has. |
| `bun run data:build` | `tools/build_leuven_data.py`: joins footprints, LiDAR, orthophotos and OSM into `data/derived/`.               |
| `bun run bake`       | `scripts/bake.ts`: keeps what lies in `AREA`, projects, simplifies and writes `public/data/city.bin`.          |
| `bun run data:check` | Rebuilds from the downloads in `data/` and fails unless the result is byte for byte the `city.bin` you had.    |

The lock is the truth: a file that doesn't hash to what the lock says for the same requests is fetched again, and if the fresh download still doesn't match, the fetch fails rather than rewrite the lock. `bun scripts/fetch.ts --update` accepts the new data, for when a source really changed upstream (the monthly workflow uses it, then reports `git diff data/sources.lock.json`). A changed request (a new query, a moved `OSM_DATE`) records its new download without `--update`.

## Pipeline

```
src/data/sources.ts ─▶ bun run data:fetch ─▶ data/{osm,grb,elevation,ortho}/ ─┐
   (the manifest)        (scripts/fetch.ts)    + data/sources.lock.json       │
                                                                              ▼
public/data/city.bin ◀─ bun run bake ◀─ data/derived/ ◀─ bun run data:build (tools/build_leuven_data.py, via uv)
```

1. **Fetch.** `src/data/sources.ts` declares every source: provider, licence, credit, the request, and where its file lands. Extents are not written anywhere: they are `AREA` (`src/data/area.ts`) plus 100 m, so growing the map grows every download. `scripts/fetch.ts` plans the requests with `src/data/fetch-plan.ts` and downloads them:
   - **OpenStreetMap** through Overpass, as it was at `OSM_DATE` (Overpass answers from its history), tiled, with failover across mirrors. An answer with a `remark` (timeout, out of memory) is a failure, not data. Tiles are merged, deduplicated and sorted by type and id.
   - **GRB** layers through the WFS, in boxes small enough to come back whole: a box that returns the 2,500-feature limit is split in four. Not `startIndex` paging: the server doesn't keep its sort order between requests, so pages skip and repeat features at their edges (the hand-paged download of October 2026 had lost 152 buildings that way).
   - **DHMV II** LiDAR through the WCS as GeoTIFF tiles of at most 1650 × 1000 px on the Lambert 72 grid (larger requests fail). Tiles are checked for the TIFF signature, since errors come back as XML with HTTP 200.
   - **Orthophotos** through the WMTS, z18 tiles over each rectangle of `AREA` plus 40 m, checked for the PNG signature.

   Network errors, 429 and 5xx answers are retried with backoff. Every source's files are hashed into `data/sources.lock.json`.

2. **Build.** `tools/build_leuven_data.py` joins GRB footprints (with their courtyards) with LiDAR heights (DSM − DTM, p90), surveys each roof (eave, share of pitched pixels, the axis its slopes face, orthophoto colour), finds church towers over the nave, finds tree crowns in the LiDAR canopy, measures GRB structures (tanks and silos get their LiDAR height, bridges keep their outline), smooths the DTM into the landform and samples it every 60 m (`terrain.json`), surveys each monument (the GRB plinth under it and its LiDAR height; see [Monuments](#monuments)), adds OSM tags and assigns a detail tier. It then runs `tools/build_road_zones.py`, which cuts the GRB road surface (WBN) along its subdivision lines (WGO: kerbs, cycle and pedestrian zones), names each face from the OSM ways running along it, and lays out lane lines, painted cycle lanes and crossings on the carriageways. Its packages are pinned in the script header and `tools/build_leuven_data.py.lock`.
3. **Bake.** `scripts/bake.ts` keeps what lies in `AREA`, projects it to local metres, simplifies it and writes the binary `LVN1` format (`src/data/format.ts`).
   - Buildings are kept whole when every corner is inside the area; ground polygons are clipped to it.
   - Footprint vertices within 0.25 m (core) or 0.5 m (fringe) of the line through their neighbours are dropped; hero footprints keep every vertex, since landmark models are fitted to them. Ground polygons lose vertices within 0.3 m, and patches of green under 25 m² go.
   - OSM areas are closed ways and multipolygon relations: a relation's outer and inner rings are joined from its member ways, open ones chained end to end, and each hole is bridged into its outer ring by a cut of no width (`bridgeHoles` in `src/data/landcover.ts`), so a ground layer stays a list of single rings and a car park keeps its grass islands.
   - Railway tracks are stored as centre lines (Douglas–Peucker to 10 cm), not polygons: the gauge is standard everywhere, so the renderer derives the ballast, sleepers and both rails. Tunnels, covered tracks and anything below ground are left out. Rails are their own layer (`City.rails`), so walking can keep off them; platforms (`City.platforms`, multipolygons joined from their outer ways) are walkable.

## Reproducibility

- **Same downloads, same bytes.** The build and bake read inputs in a fixed order, round numbers before writing them, write no timestamps, and pin the Lambert 72 transformation instead of leaving the choice to PROJ. Nothing depends on how far past `AREA` the downloads reach or how they were tiled: trees are spaced exactly and roof colours are balanced over the ring. `bun run data:check` holds them to it. It is checked on one machine at a time; floating point in the Python packages may differ between platforms, which the monthly workflow (`.github/workflows/data.yml`, on Linux) shows.
- **Same requests, (nearly) same downloads.** What each source returns over time:

  | Source        | Pinned by                       | Drifts when                                                                                                    |
  | ------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
  | OpenStreetMap | `OSM_DATE`                      | Never, unless a mapper's edit is redacted. Move `OSM_DATE` to take new edits.                                  |
  | DHMV II LiDAR | The product (flown 2013–2015)   | Never: it is a finished survey.                                                                                |
  | GRB           | Nothing: the WFS serves today's | Digitaal Vlaanderen updates footprints and roads continuously; features in this area changed in October 2026.  |
  | Orthophotos   | Nothing: "most recent" mosaic   | A new winter flight replaces it, about once a year. The dated layers (`omwrgb24vl`, …) are a different mosaic. |

  `data/sources.lock.json` records each source's files, size and hash, so `git diff data/sources.lock.json` after a fetch into an empty `data/` tells you exactly which source moved (the monthly workflow does this). Commit the lock together with `city.bin`.

## Adding a source

New data comes through the manifest and the pipeline, never by a manual download.

1. Add an entry to `SOURCES` in `src/data/sources.ts`. Pick the kind (`overpass`, `wfs`, `wcs` or `wmts`), a kebab-case `id`, its `output` under `data/`, its provider (add one to `PROVIDERS`, with its licence and credit, if it is new) and what reads it in `usedBy`. Don't write coordinates: the request follows `AREA`.
   - Another kind of service needs a planner and a check in `src/data/fetch-plan.ts` (tested) and a case in `scripts/fetch.ts`. Prefer open formats a script can read without a GIS stack: GeoJSON, JSON, GeoTIFF, PNG.
2. List it in the Sources table above and in [data/README.md](../data/README.md). The sources test fails until this page names every id.
3. Run `bun run data:fetch` (it downloads only the new source), use it in the build or the bake, then `bun run data` and `bun run verify`.
4. Commit the code, `data/sources.lock.json` and `public/data/city.bin` together. If what you draw from it is a choice rather than data, add it to [Exceptions](#exceptions).

The layers are drawn from the most generic to the most specific, a few millimetres apart: railway land, green, woods, pitches, car parks, then water, paths, the road surface and squares. ## Monuments

Statues, busts, sculptures, columns, memorial stones, fountains and pumps are each drawn as one of a few archetypes, sized, turned and coloured by what the data says about that one (`src/data/monuments.ts`, drawn by `src/scene/monuments.ts`). Of the 117 OSM points in the area that are monuments by these rules (November 2026):

| Signal                                            | Has it     | Used for                                        |

| `name`                                            | 80         | groups (a name listing several people), figures |
| `material` (and `memorial:material`)              | 42 (2)     | colour                                          |
| LiDAR height, compact and in the open (`_height`) | 25         | height                                          |
| GRB plinth or basin within 2 m (`_width`, …)      | 10         | plinth size and turn, a figure's height         |
| `height`                                          | 1          | height (the Totem)                              |
| `direction`                                       | 1          | turn                                            |
| `wikidata`, `subject:wikidata`                    | 9, 18      | not used                                        |
| `artist_name`, `start_date`, `image`              | 56, 40, 23 | not used                                        |

The LiDAR is read only where it can be trusted: within 1.5 m of the point (or on its GRB plinth), its highest pixel of 0.8 m and up; without a plinth, under 12 m and at most 8 pixels within 2.5 m over 0.3 of that height (a crown or a wall covers more); and with under a quarter of the ring 3.5–5.5 m out (2–4 m round a plinth) over 1.5 m. Statues set up after the 2013–15 flight (the 2025 KU Leuven biennale's) or under a tree get none, and neither does Fonske, where the survey has a gap over the basin, so most fall back to their tag or archetype. A reading below the archetype's least (a small duck on the quay) is drawn at the least, so it stays a few pixels. Eight of the 117 aren't drawn: two statues on a facade (Sint-Michiel, the Stadhuis' Pieter Coutereel), two of the _Listen Well_ sculptures mapped on the pumps they hang on (the pumps stay), and four with no free ground within a metre (in a courtyard, against a wall).

Wikidata is not used. Only 9 of the monuments link an item, and their OSM tags already classify them well (Fonske, the Totem, the pumps, the obelisk); items give material (`P186`) and height (`P2048`) for a few at most. Reading them would need a new kind of source (SPARQL or the entity API) whose answers can't be pinned to a date as `OSM_DATE` pins Overpass, for a handful of values OSM can carry itself: add `material` and `height` to OSM instead.

## The area

`AREA` is a few abutting, non-overlapping rectangles, so the diorama can follow the city instead of a single box: today the R23 ring with the station and its whole track bundle, and a band through Heverlee from Arenbergpark and its castle to the Abdij van Park. The slab's earth sides hang from the outline of their union, and the camera's target stays inside it.

## Growing the map

1. Change `AREA` in `src/data/area.ts`.
2. Run `bun run data`: every download follows `AREA`, so the fetch picks up the new ground and drops tiles that fell outside it.
3. Run `bun run verify`. The budgets tell you when the city got too heavy, and `baked.test.ts` when a landmark with a room has moved or changed shape (see [Rooms](#rooms)). Commit `city.bin` with `data/sources.lock.json`.

## Shop fronts

Of the OSM points in the area that are shops by `shopKind` or places by `placeKind`, and the buildings and sites that are places (November 2026), 1,474 fronts on 1,343 buildings are placed, 1,168 of them shops and 306 public places: 1,190 facing their street, 174 their square, 110 onto public ground. Left out: 52 with no footprint within 3 m, 79 with no wall facing their street, 127 mapped twice (a node and its building, the same kind on the same wall within 1.5 m; a place once a building) and 7 on landmarks. 75 of them get a terrace. A building's main front, by kind: 205 restaurant, 138 fashion, 130 other shop, 86 bar, 83 food, 74 service, 70 café, 62 snack, 57 hairdresser, 31 bakery, 29 pharmacy, 25 frituur, 24 bank, 23 books, 15 bicycle, 8 ice cream, 7 florist, 5 greengrocer. The places: 195 university, 50 school, 35 hotel, 6 sports, 5 library, 4 museum, 4 theatre, 4 hospital, 3 cinema. No police station is mapped where the bake can see it (one `amenity=police` on a building's own tags), so there is no kind for one.

Each front hangs on the drawn GRB footprint its point lies in, or the nearest within 3 m, where its point meets the wall (half a metre from the corners), on the wall that is, in order (`frontWall` in `src/data/facades.ts`):

1. the one that faces its square, when the shop is on a named square;
2. else the nearest wall that faces its street's centre line (its normal within 60° of the way there, at most 40 m off) and sees it past every other building;
3. else, for a shop down a lane or in a court, the wall nearest its street that opens onto a road or square.

`city.bin` keeps each front as its building, the edge of its footprint it stands on, how far along it and its kind (a terrace in the kind's top bit): about 4 KB gzipped.

## Places by name

The menu's search finds every named street and square in `city.bin` (`streetNames`, `streets`, `plazas` and `plazaNames`, the same names the street plate reads), so it needs no data of its own. `placesOf` (`src/data/places.ts`) gives each name one spot, the first time someone searches: a square's is the middle of its outline (a name that is both a square and a street is the square); a street's is the point on it nearest the middle of all its stretches, so it lies on the street even where it bends round a block. Choosing one calls the viewer's `walkAt`, which starts the walk on the walkable spot nearest it. The ring plus Heverlee has 489 places, 56 of them squares.

## Rooms

`public/data/rooms.json` holds the insides of the landmarks you can walk into: today Sint-Pieterskerk, with its nave and organ gallery. No open data maps the inside of a building, so it is written by hand, not fetched or baked, and the pipeline never touches it. It is about 7 KB (1 KB gzipped) and loads when the avatar comes near a landmark (`src/data/rooms.ts` reads and checks it).

Each room is keyed by its building's GRB `OIDN` (2878488 for Sint-Pieterskerk), which stays the same across rebakes, and every coordinate is in world metres, the same frame as `city.bin` ([Coordinates](#coordinates)). A room has an `id`, a `name`, a `door` (`x`, `z` on the slab's edge, and the `facing` you have going in, in radians) and its `floors`. Each floor has:

| Field           | What                                                                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `level`, `name` | 0 for the ground floor, up from there; what the street sign calls it (`Nave`, `Organ gallery`)                                                 |
| `y`, `height`   | How high it is over the building's floor, and how tall up to the next (m)                                                                      |
| `slab`          | Its outline, a flat `[x, z, …]` ring, counter-clockwise                                                                                        |
| `holes`         | Rings where the floor isn't: a stairwell, an atrium                                                                                            |
| `walls`         | Stretches from (`x0`, `z0`) to (`x1`, `z1`), with `gaps` for doorways (`[from, to]` metres along it) and an optional `height` for a balustrade |
| `props`         | Furnishings at `x`, `z`, turned by `angle`, each of a known `kind`: `pew`, `altar`, `pulpit`, `pillar`, `organ`, `font`, `chair`, `candles`    |
| `stairs`        | Flights up to floor `to`: a rectangle `width` across and `depth` long, centred at `x`, `z`, climbing toward `angle`                            |

`src/data/baked.test.ts` checks the file against `city.bin` (`roomProblems`): the building exists and is a landmark footprint (`LANDMARK_FOOTPRINTS`); every slab and hole lies inside the footprint and none crosses itself; every prop is a known kind and stands on its slab; the door is in a gap of a ground-floor wall; and every stair starts on its own floor and lands on the next one up, past its stairwell. A rebake that moves or reshapes a landmark with a room fails that test, rather than leaving a door in a wall: fit the room to the new footprint, then run it again.

To add a room, pick a landmark footprint, plot its walls from `city.bin`, write its floors, run `bun test src/data`, and look at it in the browser from all four quarter views.

## Format changes

Bump `VERSION` in `format.ts` and the cache name in `public/sw.js` together. The round-trip tests in `format.test.ts`, and `baked.test.ts`, guard the rest.
